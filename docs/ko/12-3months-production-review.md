## 3달동안 도메인 특화 에이전트를 Deploy를 했다

안녕하세요.
5월 이후로 처음 손으로 써보는 회고록? 입니다.

5월에 현재 내부망에서 제조/제약/바이오/의료 전문가들이 사용하는 챗봇 시스템을 Gemma4 26B로 적용했습니다.

이걸 3달동안 버그도 고치고.. 기능도 추가하면서 경험했던 재밌는(?) 포인트나 상당히 독특하다고 느껴진 포인트들을 손으로 적어보려고 합니다.

---
### 1. 전문가들이라고 챗봇에 제대로 물어보지는 않았다

내가 기대했던 유저:
```
약사/전문가/도메인 특화 유저(희망편) :
"우리는 이런 ~ pdf 문서를 찾아요"
"이런~ 번호를 바탕으로, 여기에 매칭되는 문서를 찾아서 리스트로 보여줄래?"
"Document-A-xxx.hwp 에 개요만 뽑아서 보여줄래?"
```

실제 유저:
```
약사/전문가/도메인 특화 유저(절망편) :
"약 A에 대한 문서있어?" (약 A에 대한 문서는 약 200건)
"아까 말한 문서랑 비슷한거 다시 찾아봐" (10번 대화 후)
"김XX 가 작성한 문서 찾아봐" ('김XX'라는 이름은 해당 회사에 6명 있음-동명이인)
```

처음 프로젝트를 배포 했을 때,

"이거.. 내부망에 돌아가는 상당히 작은 LLM이라서, 가능하면 정말 업무하듯이 구체적으로 물어보셔야합니다!"

라고 클라이언트에게 지속적으로 요청을 했고, 현장 교육도 진행했습니다.
그럼에도, 제가 처음 받은 챗 로그는

```
이거 찾아줘
저거 찾아줘
아까 말한거
왜 안되는거야?
이거 맞지?
```

였습니다.

그리고 피드백으로 받은건 
**챗 지피티는 해주는데 왜 얘는 말을 못 알아먹어요?** 였습니다.

사실 저의 입장에서는 억울했습니다. Gemma4 26B 를 Chatgpt랑 비교하면... 사실 굉장히 작고, 가벼운 로컬 모델이라 한계가 명확합니다.
그렇지만, 유저는 그런건 신경을 전혀 안쓴다는 것을 알았습니다. 유저 입장에서 이제 기준은 **Chatgpt** 입니다.

2만원만 월에 결제하면 싸게 내가 원하는 답을 대부분 그럴듯하게 다 말해주는데 왜 우리 사내망 챗봇은 못해? 그럼 챗지피티쓰지?

사용자의 눈높이는 이제 매우 높습니다. 그리고, 도메인 특화 챗봇이라고, 사용자가 **정확하고 세심하게** 물어보지 않습니다.

---
### 2. 대부분의 유저들은 2~3번 정도 대화하고 챗봇을 단편적으로 평가한다.

제가 배포한 챗봇의 로그를 확인해보니, 

```
4회 이상 챗봇과 연속해서 multi turn으로 대답한 경우 : 20%
4회 미만 : 80%

1회만 하고 평가한 경우 : 30%
```

처음 배포한 챗봇의 평가는 매우 나빴습니다.
자고 일어났더니 불만 피드백이 50건 넘게 쌓였고, 대부분의 피드백은 "얘가 답을 잘 못찾아요"였습니다.

챗봇의 첫인상은, 2~3번 미만의 채팅 로그에서 나옵니다. 사용자가 참을성을 가지고, 여러번 구체적으로 물어본 케이스에서 챗봇의 응답 만족도는 매우 높았습니다.
아까전에 'A 문서를 찾아줘' 케이스를 예시로 들면 아래와 같습니다.

```
A 문서를 찾아줘 -> 아니 그거 문서 찾을때 QA 부서로 좁혀서 -> 그치 근데 거기서 가능하면 최신 문서로 해서 찾아봐
```
를 한다면, 사용자가 처음 원했던 'A문서' 가 나옵니다.

개발하는 제 입장에서는 당연히, 이렇게 물어봐야하는거 아니야? 사용자가 A라고 했을때, 이게 QA 부서인지, 최신 문서로 말해야하는지 알 수 없습니다. (미리 이걸 설정했다면 모르겠지만)
그치만 사용자에게는 '당연히 이렇게 찾는거니까, AI도 찾았어야지' 로 평가됩니다.

이런 암묵지(tacit-knowledge)를 사전에 파악했다면 제가 적용할 수도 있었을겁니다. 그러나 이런 모든 업무의 세부적인 내용/관행/흐름을 모두 파악할 수는 없습니다.

그렇지만, 가장 큰/자주 사용하는 Impact가 큰 업무 흐름이나 기능들은 사전에 정의가 가능했었을 겁니다. 이것들을 넣어놨다면, 초기에 사용자들에게 "와 챗봇이 내가 원하는걸 잘 찾아주네?" 를 느껴질 수 있게 만들 수 있고, 좋은 평가를 바탕으로 더욱 활용율을 늘릴수 있었을 겁니다.
만약 제가 다시 작년으로 돌아간다면, 챗봇에 대한 Impact가 큰, 업무 관행과 업무 프로세스를 명시적으로라도 프롬프트에 박았을겁니다.

### 3. 클라이언트에게 지속적으로 "이게 맞나요?" 를 물어야했다

초기의 대실패 이후에,챗봇을 사용하는 클라이언트 회사와 매주 미팅을 가졌습니다. 그리고 매주 마다

```
이런 기능을 이렇게 수행하는데, 이게 맞아요?

이 테이블에, 이 컬럼은 '등급'이라고 써있는데, 이게 무슨 등급이에요?

B라는 정보를 DOC-A 라는 문서 종류에서 찾았는데 이게 업무 흐름에 맞아요?
```

이런 어찌보면 굉장히 자잘자잘한 업무 로직/데이터 거버넌스의 간격을 계속 좁혔습니다.

혹자는 이렇게 말할 수 있습니다. "이걸 왜 미리 안했나요?"

저도 후회스럽습니다. 그렇지만 약간 반론을 해보자면, 클라이언트와 초기 미팅을 가졌을때

"자 앞으로 진행하시는 업무를요, 이 형태에 맞게, 온톨로지/지식그래프 형식으로 정리해서 전부 보내주세요"

라고 저희가 요구한다면, 클라이언트가 과연할까요? 전혀 안할거라 봅니다.

그리고 업무를 정의했을때 "제대로 정리를 했을까" 에 대해서도 믿을 수 없습니다.

한달전쯤 받은 피드백중 하나는 134번 문서가 없다는 거였습니다. 그런데 134번이라는 문서는 5년전에 사라진 문서였습니다.
유저 입장에서는 "내 기억에는 134번 문서가 있는데 챗봇이 없다하는데 버그입니다" 라고 했지만, 유저의 기억이 오류였던 겁니다.

그렇기에, 지속적으로 클라이언트에게 물어봐야합니다. 클라이언트가 귀찮아하더라도 계속 물어봐야합니다.

"유저들이 그렇게 말 안해줬는데 AI가 어떻게 알아요?" 는 유저들은 이해하지도, 이해해주지도 않을겁니다

---
### 4. 챗봇의 오류나 실패는, '코드 버그' 와 '한국어 모호함' 그리고 'retrieve fail'

Gemma4 26B는 막 엄청 큰 모델은 아니지만, 상당히 탄탄한 모델은 맞습니다.

그치만 저의 처음 생각은 "모델이 작으니까 성능이 떨어져서 이해력이나 문해력이 부족하지 않을까" 라고 생각해서, AI가 답변을 제대로 생성하지 못하거나/틀렸을 경우

모델의 한계점이 아닐까로 시작했습니다.

하지만 실제 통계는 달랐습니다

```
전체 5500건의 세션에서 오류 세션은 1200건

- 430건은 적절한 문서를 retrieve 하지 못한, hit fail
- 570건은 하네스/코드/하드코딩된 필터가 "기존에 구현하지 못했던 문서 타입이나 형식/필터를 처리하지 못해서" 생긴 코드 구조상 한계
- 200건은 한국어 자체의 모호함 (ex- "그거말고 다음거는?") + 업무에서만 사용하는 관용어
- 100건만 모델의 문해력 + 기본 의료 지식 부족
```

사실상 모든 문제의 핵심은, retrieve가 되지 못한 RAG의 한계점, 버그를 해결하기 위해 넣었던 하네스/하드코딩 필터가 가져오는 Fixed filter 한계점
한국어 입력 자체가 가지는 구조적 모호성이 90%의 버그였고, 모델의 한계점은 사실상 적었습니다.

### 5. 데이터의 거버넌스 상태를 반드시 체크해야한다. (클라이언트의 말을 믿지 마세요)

"저희는 데이터 잘 관리하고 있습니다"

"MES/ERP 구축해서 데이터 거버넌스 잘 되어있어요"

절대 믿으시면 안됩니다.

특히 외산 솔루션을 쓰는 클라이언트의 경우, **반드시 raw 데이터를 확인하세요**

좋은 데이터를 가지고 있다는 업체의 실제 케이스를 하나 보여드리겠습니다.
```
[회계부서] 2023 감사 첨부1 문서 (김XX) .pdf <- 실제 메인 문서가 이거였습니다
[회계부서] 2023 감사 첨부2 -개정판 추가 문서 (김XX) .pdf
[회계부서] 2023 감사 문서 (김XX) .pdf
[회계부서] 2023 감사 문서 (김XX) .pdf
```

데이터를 잘 쌓아뒀다고 좋은 데이터가 아닌건 다들 아실겁니다.

저의 실수는, 데이터가 최소한 관리가 되고있고, 어느정도 규칙에 맞춰서 쌓여지거나 인덱싱 되고 있다고 생각했습니다.
그러나 실제로는 RawData를 확인해보니 문서 상태가 말이 아니였습니다.

꼭 확인해야합니다. 클라이언트의 말을 믿으면 안됩니다

## 마치며

프로젝트는 계속 순항(?) 중입니다.

제가 클라이언트에 대한 쓴 소리를 많이했지만, 어쩔수 없습니다. 그들은 잘못된 것에 대해서 저희의 책임을 항상 말할겁니다.

그러니 처음부터, 

**AI가 할수있는 부분**

**AI가 할 수 없는 부분**

을 명확하게 선을 긋고 가셔야합니다.

지금까지 내용들을 시시콜콜하게 아래처럼 체크리스트로 정리해보겠습니다.

- 최대한 비관적으로 모든 부분을 바라 보셔야합니다. AI, 특히 챗봇에 대한 유저의 기대치가 높습니다.
- 데이터 거버넌스가 확보된 다음에 적용을 진행하셔야 합니다. 거버넌스가 완성되지 않았다면, 점진적으로 적용하셔야합니다.
- 클라이언트 담당자에게 수시로 연락해서, 모든 에로사항과 궁금증을 지속적으로 확인하셔야합니다. 현장과 이론은 너무 동떨어져있고, 첫인상이 모든걸 결정합니다.
- UI를 가능하면, 실제 웹 디자이너를 고용해서 하셔야합니다. 이제 사람들도 AI로 만든 디자인 다 알고있습니다.
- 지속적으로 Feedback 결과를 사용자에게 보내주세요. 클라이언트는 보고용으로 이런 문서를 받는걸 굉장히 좋아합니다.
- RAG가 부족하다면, 그래프 구조를, 그래프 구조로 해도 부족한 기능은 데이터를 정리하시는게 맞습니다. 그것도 안되서 온톨로지를 하는건, 효율이 나쁩니다.
- 모델이 커진다고 좋아지는건 수치 계산 정확도와 컨텍스트 사이즈 밖에 없습니다.

실제 도메인에 AI 적용하시는 여러분 화이팅입니다.
